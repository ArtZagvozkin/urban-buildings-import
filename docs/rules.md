# Правила данных, результатов и API

## Исходники и подготовка

`config/territories.json` задаёт территории: Реутов 5231, Жуковский 5202,
Лотошино 5215, Одинцовский 5223. Тип 4 — жилое, 5 — нежилое. Жилой физический
объект имеет дополнительную запись buildings. OSM ID хранится отдельно от
серверных ID; новые ID всегда выдаёт API.

Исходные GeoJSON неизменяемы. Для завершённых результатов используется
историческая муниципальная граница из `reference/boundaries/`, совпадающая с
хешем исходной подготовки. `reproduce` не обращается к сети. Год проверки
зафиксирован в результате: 2026. Для нового импорта `prepare --live-boundary`
получает новую границу API; прежний подтверждённый результат не изменяется.

Проверяются пустые и неполигональные геометрии, валидность, самопересечения,
повторы OSM ID и нормализованной геометрии. Площадь вычисляется геодезически
на WGS84, не в квадратных градусах. `make_valid` допустим при сохранении
Polygon/MultiPolygon и изменении площади не более 0,1%; исправления отражаются
в отчёте. Геометрия должна целиком покрываться муниципальной границей.

Назначение файла должно совпадать с `is_living`. Явно жилые теги в нежилом
файле, нежилые теги и коммерческие, общественные или инженерные признаки в
жилом исключаются. Противоречивый объект не переклассифицируется без доказательства.
Исключённые объекты заново выводятся в `prepared/disputed.geojson` при prepare.

Адрес передаётся при наличии номера дома и улицы либо места. Этажность —
положительное целое до 150; год — целое от 1700 до года проверки. Отсутствующие
характеристики не выдумываются. Известные OSM-теги сохраняются в properties.

Восемь файлов Одинцова образуют полный набор территории, подтверждённый для
завершённого запуска. Части перекрываются и не задают географические сектора.
Новая территория может иметь несколько файлов одного типа; алгоритм не копируется.

## Компактный окончательный результат

`results/index.json` — единственный источник текущего подтверждённого состояния.
Он связывает территорию, запуск, идентификатор оригинального плана, файлы,
контрольные суммы, версии кода, время проверки, количества и ограничения.
`docs/status.md` формируется командой `status-doc`; тест проверяет его соответствие.

В `results/<territory>/result.json.gz` находятся:

- вид `completed-result` и версия формата;
- хеши исходников, конфигурации, исторической границы и всех тел запросов;
- карта `[osm_id, physical_object_id, object_geometry_id, building_id]` в порядке подготовки;
- сохраняемые объекты с геометрией, атрибутами, buildings и доступными связями;
- связи по ID и единый каталог связанных сервисов, без повторных копий геометрий;
- ID заменённых объектов и геометрий;
- доказательства завершения без pending и подтверждения отсутствия старых геометрий;
- идентификатор исходного неизменяемого плана и сведения об ограничениях.

Завершение операций подтверждается картами ID, итоговыми количествами, отсутствием
pending и независимой проверкой; отдельные попытки сетевых повторов не хранятся.

Тела импортированных запросов полностью выводятся из исходников и границы;
вторая копия этих геометрий не хранится. Gzip детерминирован и читается стандартным
Python. Это производное свидетельство, **не исходный master plan** и не разрешение
на повтор его выполнения. Старые планы не переписывались: необходимые поля были
проверены и перенесены до удаления прежних комплектов. Возврат базы к состоянию
до импорта не входит в цель восстановления.

Первоначальные версии всех runtime не были записаны. Их не выдаём за известные.
Сохранено и проверено точное окружение воспроизведения; новая проверка записывает
фактический commit. Существенные доказательства сохранены в компактных результатах. Рабочие
перечни удаления и история отладки не входят в проект.

## Независимая проверка

GET-выгрузка явно обходит корень и все дочерние территории, каждый разрешённый
тип и все cursor-страницы. Проверяются count, повтор ID, циклы cursor и смена
сервера. Общий include_child_territories не служит доказательством полноты.

Сверка сравнивает все OSM/server ID, типы, территории, топологию геометрий,
переданные атрибуты и buildings, сохраняемые объекты и связи. Проверяются дубли,
неожиданные объекты и отсутствие заменённых physical ID. Состояние старого apply
для проверки не требуется. Серверные данные получаются заново.

Отсутствие старых геометрий подтверждено сохранёнными свидетельствами исходных
полных проверок. `--check-old-geometries` выполняет новые GET для каждого ID;
это длительная отдельная проверка. Отчёт явно различает новую проверку и
историческое свидетельство. Один совпавший count не означает успех.

## Запись и восстановление текущего результата

API не предоставляет пакетных POST/DELETE и idempotency key. Перед записью
проверяется живая OpenAPI. Старое разрешение не действует для нового плана.

`restore-preview` получает новую серверную выгрузку и формирует неизменяемый
план: что сохранить, какие физические объекты и buildings создать, какие связи
требуют проверки. Он не планирует DELETE. Изменённые, неоднозначные и неожиданные
объекты блокируют исполнение. Планы восстановления находятся вне Git.

`restore-apply` требует отдельного разрешения по точной SHA-256 нового плана.
Использует общий журнал/состояние загрузчика и локальную блокировку. Pending POST
сначала сверяется по OSM ID, типу и геометрии. Для сохраняемых точек OSM ID может
быть None; неоднозначность останавливает исполнение. Повтор допустим только после
двух проверок отсутствия с интервалом не менее 60 секунд. Повторный запуск
продолжает то же состояние. Итог проверяется новой GET-выгрузкой по содержимому;
новые соответствия ID сохраняются в отчёте восстановления.

Прежние серверные ID восстановить не обещается. Пересоздание объекта с сервисами
требует отдельной проверки и привязки сохранённых связей к новым ID. Пока правило
не подтверждено, такой план заблокирован. Данные этих связей сохранены.

У 149 точек Реутова известны старые и новые physical ID и исходные геометрии.
Снимка до инцидента нет: прежние сторонние сервисные связи доказать невозможно.
Нынешние доступные связи сохранены и проверяются.

В Одинцове защищены объект 694562, геометрия 694559 и сервисы 735682, 736856.
Их содержимое и urban-object связи входят в компактный результат. Они не удалялись.

## Новые обычные и распределённые импорты

Рабочий поток: source → prepare → preview/backup → immutable plan → apply/resume
→ independent verify. Удаление ограничивается точными ID плана. Перед DELETE
повторно проверяются сервисы и геометрические связи; физические объекты удаляются
раньше геометрий. Общая или внешне связанная геометрия блокирует план.

Четыре worker-плана полны и не пересекаются. Владельцы удаления назначаются по
SHA-256(physical ID) modulo 4, создания — по SHA-256(OSM ID) modulo 4. Buildings
следует за физическим объектом. Глобальные GET-барьеры отделяют стадии. Worker
принадлежит переносимой папке, а не компьютеру. Две копии одного worker нельзя
одновременно запускать на разных ПК; API распределённой блокировки не имеет.
По умолчанию темп — 2,5 запроса/с на worker, барьер — не чаще раза в 120 секунд.
Связанные runtime и состояния новых запусков остаются вне Git.
